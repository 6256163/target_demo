# Shop Demo 压力测试方案（破坏性 / 极限探测）

> 与《性能测试方案》配套：性能测试回答「能不能达标」，压力测试回答「什么时候崩、怎么崩、崩在哪」。

---

## 1. 目标

1. 找到系统的**崩溃点与拐点**：并发/TPS 到多少时错误率、响应时间陡增。
2. 观察**降级与恢复能力**：压力撤除后是否自愈，MQ 堆积能否消化。
3. 定位**首个失效组件**（Tomcat 线程池 / HikariCP 连接池 / Redis / RabbitMQ / MySQL / JVM GC）。
4. 验证**超时关单、库存回滚、支付幂等**在高压下是否仍然正确（不超卖、不重复扣款）。

## 2. 压力模型

| 阶段 | 并发 | 动作 | 观察点 |
|---|---|---|---|
| P0 预热 | 10 | 2min | 缓存预热、JIT、连接池填充 |
| P1 递增 | 50 → 100 → 200 → 400 → 800 | 每级 5min，不降回 | RT/TPS/错误率曲线拐点 |
| P2 临界保持 | 拐点处并发 | 20min | 是否缓慢恶化（泄漏/堆积） |
| P3 尖峰冲击 | 拐点 ×2 | 2min 内拉起，持续 3min | 瞬时错误率、拒绝连接数 |
| P4 释放恢复 | 0 | 10min | 队列是否排空、错误率是否归零、句柄是否释放 |

停止条件（满足任一即停止加压）：
- 错误率 > 5%（持续 30s）
- P95 > 3s 或平均 RT > 1.5s
- 后端 CPU > 90% 或出现 OOM / 线程池耗尽

## 3. 分层压测（逐层剥离瓶颈）

按此顺序逐层加压，每层只让一个组件成为瓶颈，避免「一上来全链路打满」导致无法归因：

| 层级 | 压测对象 | 目的 |
|---|---|---|
| L1 | `/api/products/hot`（纯缓存读） | 测应用 + Redis 上限，DB 不参与 |
| L2 | `/api/products`（分页查库） | 测 DB 查询 + 连接池上限 |
| L3 | 下单接口（扣库存，乐观锁） | 测写冲突、行锁等待、事务耗时 |
| L4 | 支付链路（同步模式） | 测写 + 事务 + 支付状态机 |
| L5 | 支付链路（异步 MQ 模式） | 测消费者吞吐、队列堆积、消费滞后 |
| L6 | 全链路混合 | 真实流量配比下的综合表现 |

## 4. 重点观测指标

**客户端（JMeter）**：TPS、RT（avg/p90/p95/p99）、错误率与错误类型分布、活跃线程数。

**服务端**：
- JVM：堆内存曲线、GC 次数与停顿（`-XX:+HeapDumpOnOutOfMemoryError` 已开）
- Tomcat：`tomcat.threads.busy` / `tomcat.threads.config.max`（`/actuator/prometheus`）
- HikariCP：`hikaricp.connections.active/pending`（pending > 0 即连接池打满）
- MySQL：慢查询、`Threads_connected`、`Innodb_row_lock_waits`
- Redis：`used_memory`、命中率、连接数、`maxmemory-policy=allkeys-lru` 的淘汰量
- RabbitMQ：各队列 `messages_ready`（尤其 `q.payment.process`，消费端带 sleep，必然是瓶颈候选）

## 5. 预期瓶颈与验证方法

| 预期瓶颈 | 现象 | 验证方式 |
|---|---|---|
| HikariCP 打满 | RT 陡增，`connections.pending > 0` | 调大 `DB_POOL_MAX` 后重测对比 |
| Tomcat 线程池耗尽 | 连接被拒/排队，`threads.busy = max` | 调 `TOMCAT_MAX_THREADS` 对比 |
| 支付消费堆积 | `q.payment.process` 持续增长，订单长期 PAYING | 关掉 `asyncEnabled` 或增大消费者并发 |
| 库存乐观锁冲突 | 下单返回 40900 CONFLICT 增多 | 提高热点商品库存 / 降低同商品并发 |
| 缓存击穿 | 热点 key 过期瞬间 DB QPS 尖刺 | 观察 `cached=false` 比例与 DB QPS 相关性 |
| 延迟关单堆积 | `q.order.autocancel.delay` 积压，关单瞬时大量执行 | 延长压测时长到超过 TTL 后观察 |

## 6. 数据正确性与一致性校验（压后必做）

压力下正确性比指标更重要，每轮压力测试结束后执行：

1. **不超卖**：`SUM(order_items.quantity)` ≤ 商品初始库存 + 补货量。
2. **不重复扣款**：同一 `order_no` 下 `status=SUCCESS` 的支付单有且仅有一条。
3. **库存守恒**：已取消/支付失败/已退款的订单，商品库存必须回滚到下单前水平。
4. **孤儿数据检查**：不存在 `PENDING_PAYMENT` 且已超过 TTL 仍未关单的订单（补偿任务生效）。
5. **MQ 无残留**：压测结束 10 分钟后，`q.payment.process` / `q.order.paid` 队列深度应归零。

建议写成 `perf/data/consistency-check.sql` 随压测一起执行。

## 7. 环境与数据准备

- 每轮压力测试前重建库（`docker compose down -v` 或重放 `db/init`）以保证基线一致。
- 压力测试账号与性能测试账号**分池**，避免互相污染。
- 压测期间关闭前端轮询（UI 不参与），避免无关流量干扰。
- 全程仅限本地 Docker 环境执行。
