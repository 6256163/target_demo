# Shop Demo 性能测试方案（JMeter）

> 目标 JMeter 版本：**5.6.3**（`perf/Dockerfile` 中构建，未指定版本时按 skill 默认 5.6.x 取 5.6.3）
> 被测环境：本地 Docker（`http://backend:8080`，容器网络内访问，非公网/非生产）
> 状态：**方案评审稿，尚未生成 .jmx 与 CSV 数据**

---

## 1. 压测目标

1. 建立商城核心链路的**性能基线**：商品浏览、商品详情（Redis 缓存）、下单、支付。
2. 找到系统的**容量拐点**：在既定 SLA 下能支撑的最大并发与 TPS。
3. 暴露**异步链路（RabbitMQ）**的隐患：支付回调堆积、消费滞后、超时关单堆积。
4. 验证 **Redis 缓存策略**（空值缓存 / 互斥锁重建 / TTL 抖动）在热点商品下的实际效果。
5. 为后续「代码合并 → 自动回归」提供可复用的性能基线对比数据。

## 2. 被测接口清单

| # | 名称 | 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|---|---|
| 1 | 登录 | POST | `/api/auth/login` | 否 | 返回 JWT，供后续关联 |
| 2 | 商品列表 | GET | `/api/products?page&size&keyword` | 否 | 分页，直接查库 |
| 3 | 商品详情 | GET | `/api/products/{id}` | 否 | 走 Redis 缓存，返回 `cached` 标记 |
| 4 | 分类列表 | GET | `/api/categories` | 否 | 小表 |
| 5 | 加购物车 | POST | `/api/cart/items` | 是 | 写操作 |
| 6 | 查购物车 | GET | `/api/cart` | 是 | 读操作 |
| 7 | 下单 | POST | `/api/orders` | 是 | 乐观锁扣库存 + 投递延迟队列 |
| 8 | 发起支付 | POST | `/api/payments` | 是 | 落 PROCESSING，异步经 MQ 落终态 |

| 10 | 订单查询 | GET | `/api/orders/{orderNo}` | 是 | 轮询订单状态流转 |
| 11 | 后台订单 | GET | `/api/admin/orders` | ADMIN | 大表分页，压测 DB 的慢查询 |

## 3. 业务场景设计

| 场景 | 权重（混合场景内） | 步骤 |
|---|---|---|
| S1 浏览型用户 | 60% | 登录 → 商品列表（带关键字）→ 商品详情（热点/长尾）→ 分类列表 |
| S2 购买型用户 | 30% | 登录 → 加购 → 下单 → 发起支付 → 轮询支付结果（≤20 次/500ms）→ 查询订单 |
| S3 后台运营 | 10% | 管理员登录 → 后台订单分页 → 订单统计 |

- S1/S2 各用独立线程组，便于分别统计 TPS 与响应时间。
- S2 用 `Transaction Controller` 聚合成「下单支付」业务事务，统计端到端耗时。
- 思考时间：`Uniform Random Timer`（浏览 500–1500ms，下单 1000–3000ms）。

## 4. 负载模型

| 类型 | 线程数 | Ramp-up | 时长 | 用途 |
|---|---|---|---|---|
| 冒烟 smoke | 1 | 1s | 30s | 验证脚本可跑通、变量全部解析 |
| 基准 baseline | 10 | 30s | 5min | 建立基线 RT/TPS |
| 容量阶梯 load | 20 → 50 → 100 → 200 | 每级 60s | 每级 10min | 找容量拐点 |
| 混合场景 mixed | 100（按 6:3:1 配比） | 60s | 30min | 贴近真实流量比例 |
| 突发 spike | 0 → 300 → 0 | 30s 内拉起 | 5min + 5min | 观察限流/队列/连接池表现 |
| 稳定性 endurance | 100 | 60s | 2h（可选 12h） | 内存泄漏、MQ 堆积、连接泄漏 |

## 5. 断言与成功标准

- HTTP 状态码 = 200；业务 `code == 0`（JSON 断言 `$.code`）。
- 关键字段存在性：登录 `$.data.accessToken`、下单 `$.data.orderNo`、支付 `$.data.tradeNo`。
- Duration Assertion：商品详情 ≤ 500ms；下单 ≤ 1500ms；支付发起 ≤ 800ms。

**SLA 目标（本地 Docker 单机，供参考，需在 baseline 后校准）**

| 指标 | 目标 |
|---|---|
| 商品详情（缓存命中）P95 | ≤ 200ms，平均 ≤ 80ms |
| 商品列表 P95 | ≤ 500ms |
| 下单接口 P95 | ≤ 1200ms |
| 下单支付端到端 P95 | ≤ 3000ms |
| 错误率 | ≤ 0.1% |
| 浏览场景 TPS | ≥ 300 |
| 下单支付 TPS | ≥ 30 |
| 后端 CPU | ≤ 75% |
| 连接池使用率 | ≤ 80% |

## 6. 参数化与数据

- `users.csv`：`username,password`，1000 行（`user00001`~`user01000` / `123456`，由种子数据生成）。
- `products.csv`：`productId`，1000 行，**热点 : 温 : 冷 ≈ 10 : 3 : 1**（1–10 号热点商品高频出现），避免全范围随机导致缓存命中率失真。
- 多 CSV 同线程组使用时**行数必须一致、行序对齐**（用户与其购物车/订单一一对应）。
- CSV 统一 **LF 换行**，避免末尾列被 `\r` 污染（尤其是 token 列）。
- 提供 `generate_csv.py`（argparse 控制规模/随机种子），不手写死数据。
- 每个虚拟用户使用独立账号，规避重复下单与幂等冲突。

| 变量 | 来源 | 提取方式 |

| `token` | 登录响应 `$.data.accessToken` | JSON Extractor（JSONPostProcessor） |

## 8. 监控与报告

- JMeter 侧：`Backend Listener` → InfluxDB2（`http://influxdb:8086/api/v2/write?org=shop&bucket=jmeter`），Grafana 看板已预置（TPS / P95 / 平均 RT / 活跃线程 / 错误数）。
- 服务端侧：`/actuator/prometheus`（Tomcat 线程池、HikariCP、JVM）、MySQL 慢查询日志（已开 `long_query_time=0.5`）、RabbitMQ 管理台（15672）观察队列堆积。
- 产出：`result.jtl` + `-e -o` 生成的 HTML 报告，按版本号归档到 `reports/<version>/`。

## 9. 风险与前置条件

1. **仅限本地 Docker 环境**，不得指向生产/公网。
2. 压测会写入订单/支付/购物车数据，需准备清理 SQL（或每轮重建 `shop_demo` 库）。
3. 支付消费者带配置化 `sleep`，异步模式下队列必然堆积——**先跑同步模式（asyncEnabled=false）取基线，再开异步对比**，否则会把 mock 延迟误判为系统瓶颈。
4. 热点商品需先预热缓存再统计，否则首轮全是缓存穿透。
5. 超时关单延迟队列 TTL 默认 10 分钟，压测时长超过该值时会有关单任务并发执行，需关注其对 DB 的额外压力。
