# P2 用例执行说明（前置 / 步骤 / 清理）

> 对应代码：`tests/src/specs/*.api.spec.ts`（P2 44 条）+ `tests/src/specs/security.api.spec.ts`、`concurrency.api.spec.ts`、`consistency.api.spec.ts`
> 对应报告：`tests/P2执行报告.md`
> 执行方式：**必须单 worker 串行**：`npx playwright test --project=api --grep @p2 --workers=1`
> 原因：包含全局支付配置修改、并发与性能用例，多 worker 会互相污染配置与基线

## 0. 全局前置与清理（所有用例共用）

### 0.1 前置 fixture / 辅助

| 名称 | 做什么 |
|---|---|
| `runId` | 进程启动时生成一次，用于用户名/商品名去重 |
| `api` | 新建匿名 `APIRequestContext`，不登录 |
| `adminApi` | 用 `admin/admin123` 登录；P2 中大量用于读写支付配置、改商品、查统计 |
| `freshUser` / `userApi` | 每用例独立注册用户；购物车/订单/余额天然隔离 |
| `products` | 商品工厂：管理端创建并登记 id，测试结束统一删除 |
| `registerFreshUser()` | 用例内再注册一个独立用户（越权/隔离用），用完 `dispose()` |
| `support/perf.ts`（P2 新增） | `percentile`、`timed`、`concurrently`、`countBy`，用于并发与 P95 断言 |
| `support/jwt.ts` | `decodeJwt`、`signJwt`、`tamperPayload`、`noneAlgToken`、`detectJwtSecret` |

### 0.2 后置清理

| 清理项 | 做法 |
|---|---|
| HTTP 连接 | 所有 client 在 fixture teardown 或 `finally` 中 `dispose()` |
| 自建商品 | 工厂 id 逆序删除；`CART-012`/`DAT-005`/`SEC-007` 手工删除的商品重复删除时忽略错误 |
| 用户 | 无删除接口，保留 DB；每用例唯一 |
| 购物车 / 订单 / 支付单 | 无删除接口，保留 DB；按用户隔离 |
| 支付配置 | `PAY-020`、`PAY-022`、`PAY-023`、`CON-004` 在 `finally` 中恢复完整快照；`ADM-010`（P1）同 |
| 商品缓存 | `ADM-013`/`DAT-005` 依赖更新/删除自动 evict；不手动清缓存 |
| 并发遗留 | 并发用例失败的请求可能留下半成品订单/支付单，统一归属唯一用户，不影响其他用例 |

## 10. 数据残留与注意事项

- **会删除**：所有工厂商品；`SEC-007` 手工创建的商品；`CART-012`/`DAT-005` 手工删除的商品（重复删除忽略）。
- **不会删除**：用户、购物车、订单、支付单；P2 会新增较多订单/支付单（并发用例），均归属唯一用户。
- **会恢复**：`PAY-020`、`PAY-022`、`PAY-023`、`CON-004` 修改的支付配置；`finally` 中校验 code=0。
- **并发用例的副作用**：竞态失败时可能留下 PROCESSING 支付单、PAYING 订单或半回滚库存；均按唯一用户隔离，不影响其他用例；报告中的失败即为缺陷证据。
- **性能阈值**：本地目标列表/详情 P95<200ms，用例放宽到 1000ms 以避免环境抖动；混合并发 P95<3000ms。实际值记录在 `test.info().annotations`。
- **已知红 14 条**：AUTH-016、CART-013、CART-014、ORD-019、PAY-019、PAY-021、CON-003、CON-005、DAT-003、SEC-001、SEC-003、SEC-004、SEC-008、SEC-010，均为实现缺陷，详见 `P2执行报告.md` 与 `缺陷清单.md`。
