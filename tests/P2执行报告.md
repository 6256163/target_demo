## 3. 失败明细与缺陷归并

### D-P2-01 并发注册唯一约束未转业务错误（AUTH-016）

- 断言：同一用户名 8 并发注册，仅 1 个 `code=0`，其余 `409/40901`。
- 实测：仅 1 个成功，其余 **500/50000**，错误信息暴露唯一键与 SQL：
  `Duplicate entry '...' for key 'users.uk_users_username' ... insert into users ...`
- 根因：`AuthService.register` 先查重再插入，并发窗口内未捕获 `DataIntegrityViolationException`。
- 附带问题：500 响应泄露 SQL 语句（SEC-006 同类风险）。

### D-P2-02 并发加购同一商品：唯一键冲突 500 + 丢失更新（CART-013）

- 断言：10 并发加购同一商品，全部成功、单行累加、数量=10。
- 实测：多个请求 **500/50000**（`Duplicate entry 'user-product' for key 'cart_items.uk_cart_user_product'`），最终购物车数量只有 **3**。
- 根因：`CartService.add` 的“查-改-插”无锁/无重试；唯一键兜底变成 500，且并发累加互相覆盖。

### D-P2-03 加购异常入参未校验，部分类型错误 500（CART-014）

| 输入 | 期望 | 实测 |
|---|---|---|
| `productId="abc"` | 400/40000 | **500/50000** |
| `quantity="x"` | 400/40000 | **500/50000** |
| `quantity=2147483648`（int 溢出） | 400/40000 | **500/50000** |
| `quantity=1.5` | 400/40000 | **200/0**，静默按 1 写入 |

- `productId=null`、`productId` 不存在、额外字段（`snapshotPrice`/`subtotal`/`userId`/`id`）均正确：`40000` 或 `40401`，且快照价/小计取商品真实价格。
- 根因：`CartItemRequest` 只有 `@NotNull/@Min(1)`，无反序列化异常映射；小数被 Jackson 截断。

### D-P2-04 idempotencyKey 未实现，重试/并发支付产生多张支付单（PAY-019、CON-003）

- 断言：支付 TIMEOUT 后使用同一 `idempotencyKey` 重试（CON-003 为 4 并发重试），必须返回原支付单，支付单列表仅 1 张。
- 实测：重试返回新的 `tradeNo`，同一订单支付单列表变为 2 张（TIMEOUT + SUCCESS）；P2 首轮 5 并发同 key 更产生 **5 张支付单且全部 SUCCESS**。
- 根因：`PaymentService.pay` 完全未读取/持久化 `idempotencyKey`；仅靠“PAYING 时复用 PROCESSING 单”去重，`PAY_FAILED` 重试与并发窗口均会新建支付单。
- 说明：并发场景存在“请求恰好串行化”时只生成 1 张的概率，因此用例改为同 key 串行/并发重试，稳定复现缺陷；并发观测结果保留在注解中。

### D-P2-05 取消与支付竞态：取消返回成功但订单最终 PAID（ORD-019、CON-005）

- 断言：取消与支付并发后，终态唯一；若订单 PAID，则取消必须失败。
- 实测：`POST /api/orders/{orderNo}/cancel` 返回 **200/0**，但最终订单状态为 **PAID**，支付单 SUCCESS。
- 根因：`cancel` 与 `pay` 均无行锁/条件更新；`markPaid` 对 `CANCELLED` 状态没有拒绝，直接把订单覆盖为 `PAID`。
- 影响：用户看到“取消成功”，实际仍被扣款。

### D-P2-06 TIMEOUT 回滚 + 重付不扣库存 + 退款再回滚 → 库存虚增（PAY-021、DAT-003）

- 场景：下单 2 件（库存 10→8）→ 支付 TIMEOUT（回滚到 10）→ 重新支付 SUCCESS（未重新扣减，仍 10）→ 退款（`markRefunded` 再 +2）→ **库存 12**。
- PAY-021 实测重付成功后库存 **10（应为 8）**；DAT-003 实测退款后库存 **11（应为 10）**。
- 与 P0 `ORD-008` 同根因：支付成功未消耗库存，但失败/退款路径按“已扣减”假设回滚。
- 影响：库存守恒被破坏，可导致超卖。

### D-P2-07 支付单水平越权（SEC-001、SEC-008）

- 断言：他人支付单详情/列表/退款应 `403/40300`。
- 实测：B 用户可读 A 的支付单、按 A 的 orderNo 列出支付单、并成功退款（支付单 `REFUNDED`、A 的订单 `CANCELLED`）。
- 与 P1 `PAY-016` 为同一缺陷，此处从安全层（资源枚举）再次覆盖。

### D-P2-08 refreshToken/accessToken 混用（SEC-003）

- 断言：refreshToken 作 access、accessToken 作 refresh 均应 `401`。
- 实测：两者均 **200/0**，refreshToken 可访问 `/api/cart`，accessToken 可换发新令牌。
- 与 P1 `AUTH-014` 为同一缺陷，安全层复测。

### D-P2-09 LIKE 通配符注入与 categoryId 注入（SEC-004）

- `keyword=%` → `total=204`（全量）；`keyword=_` → `total=204`。
- `categoryId="1 OR 1=1"` → **500/50000**（应为 400/40000）。
- 订单号注入、登录用户名注入均正确返回 404/401，无 SQL 泄露。
- 与 P1 `CAT-008`、`CAT-009` 同源：查询未转义 LIKE 通配符、参数类型异常未映射。

### D-P2-10 Actuator 端点过度暴露（SEC-010）

- 断言：API.md §1.1 仅承诺 `/actuator/health/**`、`/v3/api-docs/**`、`/swagger-ui/**` 匿名可访问。
- 实测匿名 **200**：`/actuator/metrics`、`/actuator/prometheus`、`/actuator/info`。
- 根因：`management.endpoints.web.exposure.include=health,info,metrics,prometheus,httpexchanges`，且 `SecurityConfig` 以 `anyRequest().permitAll()` 兜底。
- 影响：指标、JVM/HTTP 统计等内部信息对外暴露。
