## 3. 失败明细与缺陷归并

### D-P1-01 JWT 无效/过期时 `/api/auth/me` 返回 500（AUTH-012、AUTH-013）

- 断言：篡改 payload / 过期 accessToken 访问 `GET /api/auth/me` 应 `401/40100`（API.md §3.1「需要登录」）。
- 实测：HTTP **500 / 50000**。
- 根因：`/api/auth/**` 在 `SecurityConfig` 中为匿名可访问，`JwtAuthenticationFilter` 对签名失败/过期仅清空上下文不拦截，`AuthController.me()` 内 `CurrentUser` 取不到用户直接抛异常，被兜底为 500。
- 同用例中篡改 token 访问 `/api/admin/products` 已正确返回 401，说明过滤链本身能拒绝，仅 `/me` 的匿名分支异常。

### D-P1-02 refreshToken 与 accessToken 可互换（AUTH-014）

- 断言：refreshToken 不得作为 access 访问受保护接口；accessToken 不得用于 refresh。
- 实测：refreshToken 访问 `GET /api/auth/me` → **200/0**；accessToken 调用 `POST /api/auth/refresh` → **200/0** 并换发新令牌。
- 根因：令牌签发含 `typ` claim，但校验/刷新均未校验 `typ`。

### D-P1-03 累计加购可突破库存（CART-007）

- 断言：已购 1 件、库存 10，再次加购 10 件（合计 11）应 `409/40903`。
- 实测：**200/0**，购物车数量 11 > `availableStock=10`。
- 根因：`CartService.add` 仅校验单次 `quantity <= stock`，未校验与已有数量之和。

### D-P1-04 修改购物车数量边界缺失（CART-008）

| 输入 | 期望 | 实测 |
|---|---|---|
| 修改为 11（库存 10） | 409/40903 | **200/0**，数量 11 |
| 修改为 -1 | 400/40000 | **200/0**，条目被静默删除 |
| 请求体缺少 `quantity` | 400/40000 | **500/50000**（`quantity` 为 null 触发 NPE） |

### D-P1-05 空购物车清空未返回 40905（CART-009、CTR-003）

- 断言：API.md §3.4 规定空购物车清空返回 `409/40905`。
- 实测：**200/0**，`totalAmount=0`。
- 同时导致 `CTR-003` 错误码映射矩阵中 40905 一项失败。

### D-P1-06 成功响应缺少 traceId（CTR-001、CTR-008）

- 断言：API.md §1.2 信封示例包含 `traceId`，且「所有接口返回统一信封」。
- 实测：成功响应无 `traceId` 字段；业务错误响应有（16 位十六进制），安全 401/403 无。
- 根因:`ApiResponse.ok()` 未设置 traceId，仅异常处理器设置。
- 说明：用例清单 CTR-001 曾记录「源码 ok() 未设置」这一实现事实；按本项目「以 API.md 为唯一 oracle」的约定，测试仍断言文档，保持红色。

### D-P1-07 401/403 中文 message 乱码（CTR-003）

- 断言：`message` 分别为「未登录或登录已过期」「无权限访问」（API.md §1.2）。
- 实测：`?????????` / `?????`，响应头 `Content-Type: application/json;charset=ISO-8859-1`。
- 根因：`SecurityConfig` 直写响应时使用默认 ISO-8859-1，未设置 UTF-8。

### D-P1-08 商品分页 size 非正数返回 500（CAT-007）

- 断言：`size=0`、`size=-1` 应 `400/40000`。
- 实测：**500/50000**（`PageRequest.of` 抛 `IllegalArgumentException`）。
- 另：`page=-5` 被实现钳制为 0，`size=10000` 收敛为 200，均已在用例内记录为基线。

### D-P1-09 keyword 未转义 LIKE 通配符（CAT-008）

- 断言：`%` 未在文档声明为通配符，应作为普通字符，不应命中全量。
- 实测：`keyword=%` → `total=206`（全量）；`keyword=_` 同样命中大量数据。
- 根因：查询直接拼 `like %keyword%`，未转义 `%`/`_`。
- 同用例的中文、大小写、注入串（`' OR 1=1--` → 0 条）均通过。

### D-P1-10 categoryId 非数字返回 500（CAT-009）

- 断言：`categoryId=abc` 应 `400/40000`。
- 实测：**500/50000**（`MethodArgumentTypeMismatchException` 未映射）。

### D-P1-11 超长收货信息导致 500（ORD-009）

- 断言：API.md 未限制收货信息长度，超长输入应 4xx 或截断，不应 500。
- 实测：`receiverName=300 字 / phone=100 位 / address=600 字 / remark=300 字` → **500/50000**（数据库列长度异常未转换为 40000）。
- 其余参数校验（items 空/缺失、qty 0/-1、productId 不存在、库存不足）均通过。

### D-P1-12 订单状态不允许支付时错误码错误（ORD-014）

- 断言：API.md §3.6 明确 `40904`（订单状态不允许支付）。
- 实测：已取消、已支付订单再次支付均返回 **409/40906**（支付单状态不允许操作）。
- 未重复扣款、未生成第二张支付单，仅错误码口径与文档不一致。

### D-P1-13 管理端非法发货/收货静默成功（ORD-015、ADM-009）

| 操作 | 期望 | 实测 |
|---|---|---|
| 未支付订单发货 | 409/40904 | **200/0**，状态仍 `PENDING_PAYMENT` |
| 未支付订单确认收货 | 409/40904 | **200/0**，状态不变 |
| `DELIVERED` 后重复发货 | 409/40904 | **200/0** |
| 重复确认收货 | 409/40904 | **200/0** |
| 已取消订单发货 | 409/40904 | **200/0**，状态仍 `CANCELLED` |

根因：`markShipped`/`markDelivered` 对不满足前置状态的分支直接 `return`，未抛 `40904`。

### D-P1-14 fromCart=true 空购物车错误码不一致（ORD-023）

- 断言：API.md §3.5 要求 `409/40905`。
- 实测：**400/40000**（`下单商品不能为空`）。
- 失败下单未落库，库存未变化。

### D-P1-15 支付入参缺少校验（PAY-011）

| 输入 | 期望 | 实测 |
|---|---|---|
| 缺少 `orderNo` | 400/40000 | **404/40402** |
| `orderNo=""` | 400/40000 | **404/40402** |
| `payType=BITCOIN` | 400/40000 | **500/50000** |
| `outcome=MAYBE` | 400/40000 | **500/50000** |

根因：`PayRequest` 无 `@Valid`/枚举反序列化异常未映射。`idempotencyKey` 超长未导致 500（通过）。

### D-P1-16 回调入参缺少校验（PAY-012）

| 输入 | 期望 | 实测 |
|---|---|---|
| 缺少 `status` | 400/40000 | **500/50000** |
| `status=NOPE` | 400/40000 | **500/50000** |
| `callbackId` 500 字符 | 不应 500 | **500/50000** |

同用例的正常回调、同 `callbackId` 重复回调幂等、不存在 tradeNo → 40403 均通过。

### D-P1-17 支付单水平越权（PAY-016，严重）

- 断言：他人支付单详情/列表/退款应 `403/40300`。
- 实测：B 用户使用 A 的 tradeNo：
  - `GET /api/payments/{tradeNo}` → **200/0**，返回完整支付单；
  - `GET /api/payments?orderNo=...` → **200/0**，返回 A 的支付单列表；
  - `POST /api/payments/{tradeNo}/refund` → **200/0**，支付单变 `REFUNDED`，A 的订单被置 `CANCELLED`。
- 根因：`PaymentService.get/listByOrder/refund` 均未做归属校验（`CurrentUser.id()` 未参与查询）。

### D-P1-18 清商品缓存接口为空实现（ADM-008）

- 断言：API.md §3.7 清缓存后详情应重新回源（`cached=false`）。
- 实测：接口返回 `true`，但随后详情仍 `cached=true`，Redis key 未删除。
- 同用例的「其他商品缓存不受影响」「更新商品自动失效」均通过。

### D-P1-19 支付配置越界值被接受（ADM-010）

| 输入 | 期望 | 实测 |
|---|---|---|
| `failureRate=1.5` | 400/40000 | **200/0** |
| `failureRate=-0.1` | 400/40000 | **200/0** |
| `timeoutRate=1.5` | 400/40000 | **200/0** |
| `minDelayMs=-1` | 400/40000 | **200/0** |

- `minDelayMs > maxDelayMs` 已由服务层正确拒绝（400/40000），通过。
- 根因：`PaymentConfigRequest` 有 `@DecimalMin/@DecimalMax/@Min` 约束，但控制器入参缺少 `@Valid`。
- 每个用例均在 `finally` 恢复原配置，执行后基线未被污染。

### D-P1-20 商品 status 未按枚举校验（ADM-015）

| 输入 | 期望 | 实测 |
|---|---|---|
| 新建 `status=BAD` | 400/40000 | **200/0**，落库 `BAD` |
| 新建 `status=on_sale` | 400/40000 | **200/0** |
| 更新 `status=INVALID` | 400/40000 | **200/0** |

- `name` 空/缺失、`price=0/-1`、`stock` 缺失均正确返回 400/40000；`price=0.01, stock=0` 合法边界通过。

## 4. 本轮测试代码修正（非缺陷）

| 用例 | 问题 | 修正 |
|---|---|---|
| AUTH-009 | 短用户名由 `runId` 前缀截断生成，长度 3/64 时与其他运行冲突返回 40901 | 改为全随机字符 + 冲突重试；`password` 矩阵同时比较 HTTP 与 code（原矩阵把 200 写成 0） |

## 5. 已记录并固定的实现基线（用例通过）

以下行为 `API.md` 未定义，用例断言实现现状并在报告中标注，避免后续误判：

- `CAT-011`：用户端商品列表/详情不过滤 `OFF_SALE`。
- `CAT-007`：`size=10000` 收敛到 200，`page=-5` 钳制为 0，`page` 超界返回空页且 `last=true`。
- `CART-003`：同商品重复加购为单行累加（P0 已覆盖），累计超库存见 D-P1-03。
- `CART-009`：重复删除、删除不存在条目均返回 200/0（幂等）。
- `ORD-010`：同一商品多行不合并，按行建明细、按行扣库存。
- `ORD-012`：管理员可读取任意用户订单详情（`assertOwnership` 对管理员放行）。
- `ORD-021`：自动关单只置 `CANCELLED`，不生成/关闭支付单（`CLOSED` 未实现）；本轮环境跳过。
- `PAY-013`：`PaymentStatus.CLOSED` 无自然触发路径，未覆盖。
- `PAY-015`：手动回调与 MQ 竞争后终态唯一，后到回调不反转状态。
- `ADM-012`：管理端订单列表与用户端订单 Schema 一致；列表无显式排序。
